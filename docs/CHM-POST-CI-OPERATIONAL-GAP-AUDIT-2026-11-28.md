# CHM-SFD — تقرير تدقيق الفجوات التشغيلية بعد نجاح CI
**التاريخ:** 2026-11-28  
**فرع العمل:** `chm-final-ui-requirements-2026-11-26`  
**النسخة المفحوصة:** `d44b7bb14487bb7c8dd87719f6beba34ff43cfb5`

## 1. نتيجة التحقق الآلي
اجتاز GitHub Actions على قاعدة PostgreSQL مؤقتة ونظيفة: تثبيت الحزم، توليد Prisma Client، تطبيق جميع migrations، الفحص الثابت، TypeScript، وبناء Next.js. هذه نتيجة تحقق هندسي للشفرة والمخطط على قاعدة جديدة؛ ولا تعني اجتياز اختبار المستخدم النهائي أو سلامة سجل migrations الموجود على فرع Neon الحالي.

## 2. مسارات ثبت أنها تستخدم API وقاعدة البيانات
- العمليات: صفحة الإدخال ترسل إلى `POST /api/operations`، ومخزن الواجهة يجلب القائمة من `GET /api/operations`، والتحديثات تستخدم `PATCH /api/operations/[id]`.
- صناديق الشكاوى ومحاضر الفتح: الواجهة تتصل بـ `/api/complaint-boxes` و`/api/complaint-boxes/minutes` وتحديث الصندوق عبر `/api/complaint-boxes/[id]`.
- التوعية الميدانية: الحفظ عبر `/api/field-awareness`؛ التخزين المحلي في صفحة النشاط خاص بمسودة الإدخال المؤقتة.
- المتابعة الميدانية: الحفظ والقراءة عبر `/api/monitoring`.
- المستخدمون: القراءة والإضافة والتفعيل عبر `/api/admin/users` مع تحقق خادمي من جلسة مدير النظام.
- المراجع: المشاريع والمواقع والتصنيفات لها مسارات API مستقلة.

## 3. فجوات مثبتة تحتاج معالجة قبل اعتماد التشغيل
1. **المخزن العام ما زال يحتفظ بنسخة محلية من بيانات غير المصادقة:** `lib/store-context.tsx` يقرأ ويكتب `sfd-complaints-v1` في localStorage. كما أن واجهة المخزن تعرض حقولاً وإجراءات محلية للتحليلات والمتابعة والمخزون وطلبات المخزون؛ يلزم نقل ما يستخدم فعلياً إلى APIs مركزية أو حذف المسارات القديمة بعد إثبات عدم استخدامها.
2. **المخزون:** صفحة `app/(main)/inventory/page.tsx` لا تُظهر اتصالاً مباشراً بـ API في مراجعة المصدر؛ يلزم استكمال CRUD مركزي للمخزون وطلبات المخزون قبل اعتبار الوحدة تشغيلية.
3. **الإجراءات التصحيحية:** صفحة `app/(main)/corrective-actions/page.tsx` تعتمد على `ALL_PROJECTS_DATABASE` المحلي، وتحتوي أرقاماً وسجلاً ثابتاً، وزر الحفظ يعرض رسالة نجاح دون طلب API. يجب ربط المشاريع بمرجع المشاريع المركزي وإنشاء سجل إجراءات تصحيحية حقيقي.
4. **التقارير:** يلزم مراجعة مصدر الأرقام والتجميعات والتصدير في صفحة التقارير والتأكد من أنها تستعلم من البيانات الفعلية فقط، لا من بيانات ثابتة.
5. **سجل العمليات:** صفحة السجل تستخدم `operations` من مخزن الواجهة، لذا يعتمد عرضها على نجاح جلب API. يجب اختبار حالات التحميل والخطأ، والتحقق من أن فتح التفاصيل وتحديثها يعملان بعد تسجيل الدخول.
6. **توحيد قاعدة المصادقة:** Better Auth ما زال يستخدم PostgreSQL عبر `pg.Pool` وDrizzle في `lib/db`، بينما بيانات التشغيل تستخدم Prisma. هذا الفصل قد يكون مقصوداً حالياً، لكنه يحتاج قراراً معمارياً موثقاً واختبارات تكامل قبل توحيد المسار أو تغييره.
7. **Neon validation:** لا يُسمح بتطبيق migrations على فرع Neon الحالي حتى تتم مطابقة حالته الفعلية مع migrations؛ نجاح قاعدة CI النظيفة لا يثبت تطابق الفرع الموجود ولا يعالج DDL اليدوي السابق.

## 4. ضوابط الاستمرار
- لا تعديل على `main` ولا على إنتاج Vercel.
- لا تنفيذ migrations أو استيراد بيانات على Neon الحالي في هذه المرحلة.
- لا اعتبار بيانات localStorage أو الأرقام الثابتة سجلات مركزية.
- أي وحدة لا تملك API وحفظاً واختباراً فعلياً تُوسم «غير مكتملة» بدلاً من عرض نجاح شكلي.

## 5. ترتيب الإصلاح المقترح
1. توثيق خريطة الوحدات النشطة ومصدر بيانات كل شاشة.
2. استكمال API والصلاحيات وسجل التدقيق للمخزون والإجراءات التصحيحية والتحليلات والمتابعة.
3. إزالة اعتماد الواجهات النشطة على بيانات المشاريع الثابتة وربطها بمراجع API.
4. استكمال اختبارات الوظائف على Preview محمي بعد استعادة الوصول الموثق إليه.
5. تسوية migrations مع فرع Neon بعد نسخة احتياطية ومراجعة المخطط وموافقة منفصلة.
6. اختبار المستخدم المحلي على ZIP، ثم مراجعة Preview؛ لا نشر إنتاجي دون اعتماد المستخدم.

**الخلاصة:** نجاح CI يزيل عائق البناء والمهاجرات على قاعدة جديدة، لكنه لا يجعل النظام مكتملاً تشغيلياً بعد. الفجوات أعلاه تمنع وصف النسخة بأنها جاهزة للإنتاج.
